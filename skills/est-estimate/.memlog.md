- (decision) Skill est-estimate: skill #2 of the BMad Delivery Estimator module (code est), the core engine. Built from skills/reports/estimation-module-plan.md — the Cost Model Specification is the authoritative source for every formula and seed coefficient.
- (decision) Input boundary is strict: est-estimate consumes a Feature Inventory only, never raw documents. Given a PDF or a folder it points at est-scope-extract rather than chaining. The user chose this over auto-chaining because a bad inventory silently produces a confident wrong number, and the human review of extraction is what catches invented scope.
- (decision) Cost model is cost-model.json, not cost-model.md as the plan originally said. The user asked for a single machine-readable source of truth so output can be consumed programmatically rather than re-typed. Inspectability is preserved by giving every coefficient a 'why' field inline — the same standard the module already applies to feature tags and completeness signals, so the file explains itself without a companion document.
- (decision) estimate.json is likewise the source of truth for output; the markdown, CSV and interactive HTML are projections regenerated on demand. Mirrors the feature-inventory.json pattern from skill #1.
- (decision) Planning artefact volume is derived from the feature set — epics from feature count, stories weighted by size band, plus the fixed document set — so planning_review_h scales sublinearly with scope the way real planning does, and remains reproducible for unattended runs.
- (decision) Interactive HTML report built now, not deferred: per-feature components embedded as JSON and the PERT aggregation re-run client-side on every feature toggle, making the estimate a live scope-negotiation tool.
- (note) Binding build standards carried from skill #1: verify guarantees by script rather than asserting them; every judgement input carries a why enforced by script; every human gate names a conservative unattended default logged as a memlog assumption; arithmetic, PERT aggregation, critical path and role allocation are all script work; adversarial fixtures reused from skills/est-scope-extract/evals/; Analyze lenses before shipping.
- (note) The central modelling insight that must not be flattened: review_h is driven by manual_baseline, not by the compressed build_h, because review scales with the volume of output produced rather than the time taken to produce it. Compression shrinks build and leaves review untouched, which is why a payments feature stays expensive while CRUD collapses.
- (decision) Tightened the planning_review coefficients. A test of the plan's own claim — that planning review carries a visibly narrower band than everything else — failed at scale: per-story review uncertainty is correlated (if the reading rate is wrong it is wrong for every story) so it scales linearly, while feature variance combines in quadrature and shrinks relatively as features accumulate. The original coefficients did not express how genuinely predictable reading a known artefact at a known rate is. Tightened so the anchor claim is true by measurement rather than by assertion.
- (decision) Corrected a real modelling error found by a failing test: manual_equivalent was being compared against the whole-project total, but it only ever summed the features' manual baselines. Planning, environments, QA and client overhead are costs a manual project pays too, so the comparison was apples to oranges and 'implied compression' was a fake number. Now reports build_compression only — manual build effort against BMad build effort — with whole_project_compression explicitly null and an inline explanation of why.
- (note) Commercially significant consequence: an 8x BUILD compression is not an 8x cheaper project. On a five-feature routine sample the build compresses about 7x while the project total still exceeds the features' manual baseline, because planning, infra, QA and overhead do not compress. est-agent-estimator will need this when defending a number, and the company should not pitch build compression as project compression.
- (decision) Probing degenerate inputs found two real problems. (1) An empty inventory returned 68.9h — planning documents and environments for no scope at all, a confident number for nothing. Now refused with an error naming the likely cause. (2) Summing feature variances in quadrature assumes feature errors are independent, which they are not: if the size-band or compression calibration is off it is off for every feature at once. A hundred-feature scope was therefore reporting a ±15% band, which is not credible for an uncalibrated model. Added uncertainty.model_risk (0.15 while uncalibrated), combined in quadrature with the feature-level sd, and both terms are now reported separately in the estimate's confidence block. est-calibrate should lower model_risk once backtesting shows how far the model actually lands from actuals.

- (event) Analyze determinism lens found two CRITICAL defects, both confirmed by reproduction. (1) The interactive report's JavaScript omitted the model_risk term, so the page rendered 501-714h where the document said 402-813 — 52 percent of the real range — beneath a headline that included it. The runtime self-check stayed silent because it compared only the mean. Cause: model_risk was added to the engine after the template was written, and the manual node check I ran had been run before that change. (2) narrowing_questions computed its baseline with a different formula from the headline, so every reported band reduction carried the whole model_risk term: a no-op mutation reported a 198h saving and all six real questions reported an identical 205h. The JS mirrors it explicitly and the self-check now compares low, likely and high rather than the mean alone. Question values dropped from a phantom 205h (49.9 percent) to a plausible 17.5h (4.3 percent).
