- (decision) Skill est-calibrate: skill #4 of the BMad Delivery Estimator module (code est). Turns real spent hours into evidence-backed cost-model adjustments. Built from the plan's est-calibrate brief, against the ledger entries est-estimate writes.
- (decision) Partial-data policy: conservative now, regression later. From project totals alone, calibrate only what totals honestly support — band width via model_risk, and a global sizing scale. Per-tier and per-class coefficients need attribution and are refused without it, with the reason stated. A regression path unlocks when the ledger holds enough projects AND their mix is genuinely varied.
- (decision) The regression gate is NOT sample size alone. Projects that all have the same composition cannot separate the coefficients no matter how many there are, so the guard is the condition number of the design matrix as well as a minimum project count. An ill-conditioned fit is refused with that as the stated reason.
- (decision) The accuracy report leads with band hit rate — how often the actual fell inside the quoted range — because that is the honest measure for a ranged estimator and the one that directly calibrates band width. Typical error size follows.
- (decision) model_risk is calibrated from the variance of standardized residuals: r = (actual − likely) / sd. If the model were calibrated the spread of r would be 1.0; an observed spread of 1.8 means the model understates its own uncertainty by that factor, and model_risk is solved to compensate. This needs project totals only, so it is the day-one win and the first thing the company can honestly calibrate.
- (decision) Readiness mode: with no actuals in the ledger the skill reports what capturing them would unlock — which fields matter and which coefficients each granularity level makes calibratable — rather than failing. The company has no closed BMad projects yet, so this is the mode it will actually run first.
- (decision) Approval is one batch: every proposal in a single table with old value, new value, evidence, sample size and its backtest result, accepted or rejected individually. No auto-accept — that would break the no-silent-drift rule the module rests on.
- (note) Build standard #7 from skill #2 applies directly: backtesting must call est-estimate's own engine rather than reimplement pricing. In skill #2 a second implementation of one quantity made every reported figure the gap between two formulas.
- (note) Robust statistics throughout: median and MAD rather than mean and sd, so one unusual project cannot move a coefficient. Outliers are reported, not silently dropped.
- (event) Ground-truth validation found a real statistical defect before any of it shipped. Band-width detection at a moderate effect size was only about 60 percent reliable across seeds, because the residual-spread statistic is itself noisy at small sample sizes — measured over eight projects an observed spread of 1.13 is indistinguishable from 1.0. The original fixed 0.15 dead-band ignored sample size entirely and would have proposed band changes on sampling noise.
- (decision) The dead-band now scales as max(0.15, 1.5/sqrt(n)), so a deviation must clear roughly the sampling error of its own estimate before a proposal is raised. With eight projects that requires a spread past 1.53; with fifty, past 1.21. The cost is needing more projects or a genuinely wrong band before the calibrator says anything, which is the right trade for a tool whose whole value is being trusted.
- (decision) The regression gate judges the RANGE of each tier's share across projects, not its spread. Two fixtures in a row exposed why: a set of projects built to one recipe still showed 0.50 of spread purely from random feature sizes, which is genuine separable variation and the guard was right to accept it. Range at least 0.45 in two or more tiers means someone actually delivered a payments-heavy project and a CRUD-heavy one.
- (note) Both fixture bugs were the same mistake: a fixture claiming uniformity that was not uniform. Fixing it required pinning feature sizes as well as tier counts, because the guard measures share of hours rather than share of features.
- (event) 11 ground-truth cases hold, covering both directions of every claim: detects under- and over-estimation, proposes nothing when the model is right, calibrates band width from totals alone, refuses to move the band on a noisy spread, ignores a single outlier, refuses below the sample threshold, targets the right coefficient given phase-level actuals, excludes scope-changed projects rather than averaging them in, refuses regression on uniform project shapes, and falls back to readiness when nothing has actuals.
- (event) Analyze customization lens found a real bug: the band-hit target 0.68 was hardcoded in both analyze.py and backtest.py, but it is a function of the model's own uncertainty.z — and the cost model explicitly invites a user to set z=1.28 for an 80 percent band. A company taking that advice would have had its correctly calibrated ranges judged far too wide and narrowing proposed. The target is now derived as erf(z/sqrt(2)): 68 percent at z=1.0, 80 at 1.28, 90 at 1.645.
- (decision) Promoted MIN_MIX_RANGE, SHRINKAGE_K and the phase dead-band to CLI flags, on the customization lens's reasoning that they gate exactly what --min-samples already gates — whether the calibrator is allowed to speak — so exposing two and burying three was arbitrary. The lens also ruled that none of these belongs in customize.toml: a numeric statistical constant has no shape in that contract, and declaring one would be the opaque-scalar abuse the guide forbids.
- (event) Analyze enhancement lens found three real gaps, all applied. (1) The workspace token was used in four commands and never defined, and no memlog was inited — so an approval batch interrupted mid-decision was unrecoverable. {workspace} is now bound to a dated calibration folder, the memlog is inited at the start of a run, and each accept/reject/defer is logged as the human gives it. (2) Readiness — the mode this company will run for months — had one clause of procedure, was never routed to the renderer, and analyze.py exited with an error on an empty ledger, which is literally day one. It now has its own section, treats an empty ledger as readiness, and leads with an actionable chase list of estimates that went out and never came back with hours, oldest first, each with the command to run. (3) No accuracy distillate existed for skill #3; accuracy-brief.json now carries the headline figures and pending proposals without the internals.
- (event) Analyze determinism lens found four statistical defects, all confirmed by reproduction. (1) CRITICAL: MAD returns exactly zero whenever more than half a sample shares a value — routine below ten projects — and an unguarded zero cleared any tolerance and drove model_risk to zero, proposing a band of no width from five projects. (2) The regression gate's 0.45 range threshold was compared against ONE standard deviation of composition noise, but the relevant null is the expected RANGE of that noise, which grows with sample count: simulation showed the gate passing on pure noise 61 percent of the time at eight projects and 91 percent at sixteen. (3) The entry sd was re-derived by dividing the raw error by the residual z it was built from, creating a zero-denominator case handled two different ways — dropped in one place, medianed in as zero in the other, dragging model_risk toward nothing. (4) The band was sized by removing the full measured bias while the sizing proposal applies only the shrunk factor, and removed it even when no sizing proposal was raised at all.
- (decision) The regression gate now compares each tier's observed span against the expected range of sampling noise for projects of that size, using the control-chart d2 constant, with a 1.5x margin. Verified: it passes 2 of 12 noise-only fixtures where the old threshold passed 61 to 91 percent, while still accepting genuinely varied sets. This is the second time this guard was wrong in the same family — the first fix replaced a spread threshold with a range threshold and still compared against a single deviation of noise.
- (decision) Proposal order now matters and is explicit: the sizing proposal decides how much systematic error will actually be corrected, and the band is judged on whatever that leaves behind. The analysis reports the correction assumed and says so in correction_note, because sizing a band for a correction only partly made leaves it too narrow.
